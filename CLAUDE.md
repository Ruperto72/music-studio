# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Web Audio Studio — a browser-based 8-bit chiptune editor. Everything is synthesised live with the Web Audio API: no audio files, no dependencies, no build step. The entire app is a single self-contained `index.html` (HTML + CSS + JS in one file) plus a small song-data module.

It was extracted from the [Frog vs Toad](https://github.com/Ruperto72/frogger-multiplayer) game; that game's soundtrack ships here as the demo song.

## Commands

```bash
node dev-server.js        # serve the repo root at http://localhost:8080
node dev.js                # same, but also opens it in your default browser once it's up
start.cmd                  # Windows: double-click to do the same (just runs `node dev.js`)
node verify.js              # headless smoke test — see below
```

Any static file server works (e.g. `python3 -m http.server 8080`) — a server is required because ES modules don't load from `file://`. There is no build or lint command, and no test framework; there are no dependencies to install. `verify.js` is the closest thing to a test command: a single, permanent, dependency-free regression check (see its own section below) — not a substitute for actually exercising a change in a real browser, but a reusable net for the kind of "did I break something" question that used to mean writing a one-off Playwright script by hand every time.

## Architecture

- **`index.html`** — the entire application (~3800 lines) inside a single `<script type="module">`. There is no component framework and no bundler; everything is plain DOM manipulation (`createElement`, `addEventListener`) driven by a central `state` object and a `render()` function that rebuilds the DOM from state. Treat this file as several logical sections rather than a list of functions:
  - **State & song model** — `state` holds tracks, notes/hits, selection, playhead, loop range, grid, tempo, mix (gain/pan/mute/solo), per-track automation curves, per-track ADSR envelopes, history stack, etc. Tonal tracks store notes as `{start, dur, ...}`-style objects; rhythm tracks store hits (10 types: kick/snare/rim/hihat/openhat/shaker/tom/clap/crash/ride, `RHYTHM_ROWS`), each with an optional `vel` (0.1–1, **absent means full** — see `hitVel()`, and note that the inspector deletes the property rather than storing `vel: 1`, so a song that never touched velocity serialises exactly as before). There can be more than one rhythm track — all share the same fixed 10-piece kit, always stay grouped after every tonal track (`RHYTHM_TRACK_IDS`, mirroring `PITCH_TRACKS`), and at least one always exists. Helper functions like `toColumnNotes`/`fromColumnNotes` and `toColumnHits`/`fromColumnHits` convert between the internal sequence format and the grid-column representation used for editing. The built-in grooves the 🥁 Patterns dialog stamps in live in one table, `RHYTHM_PATTERNS` — each entry is a one-bar `hits` list authored at 8 eighths/bar (`insertPatternIntoRhythm()` scales to the song's real `eighthsPerBar()`), plus a one-bar `fill` in the same shape. A `start` may be fractional — the column unit is an eighth but positions re-lattice to `MICRO` (1/6 of one), so `0.5` is a 16th and `1/3` a triplet, the same lattice the grid dropdown offers. Three optional fields let a pattern bring editor state or a behaviour change with it: `swing` → `state.swing` (shuffle isn't shuffle without it), `grid` → `state.grid` (**a 16th-note groove must set this**, since a hit's block is drawn one *grid step* wide, so two 16ths on the default 1/8 grid render one on top of the other), and `crashAfterFill: false` to decline the crash the bar after a fill (bossa nova's fill flips the clave rather than building). Hits carry `vel` under the same **absent means full** rule as everywhere else, so `patternHitAt()` only copies the property across when it is actually below 1. Fills land on the last bar of each `patternFillEvery`-bar phrase (`FILL_EVERY_CHOICES`, counted from the *insert* bar rather than bar 1 of the song) and the bar after a fill opens with a crash — added through `hitsConflict()` rather than blindly, since Breakbeat already crashes on its own downbeat. **A new groove is one table row**, `fill` included; nothing about phrasing or velocity is per-pattern code.
  - **Autosave / undo / history** — `autosave()` persists the current song to `localStorage` in the background as a crash-recovery safety net; it's write-only, never read back automatically — the page always boots into a blank project (just a Rhythm track, see the state-init block right after `applySavedMix()`) rather than restoring that draft or loading the demo song, so song selection always goes through the explicit 🎵 Songs menu instead. `commitHistory()`/`undo()`/`redo()` maintain a separate in-memory snapshot stack (`snapshotSong()`/`restoreSnapshot()`) for the current session's own undo history.
  - **Rendering** — `render()` is the single entry point that redraws tracks, timeline, markers, playhead, loop handles, and scrollbar. Track lanes are rebuilt per-render (`renderTracks`, `renderPitchTrack`, `renderRhythmTrack`), with an optional extra automation-curve row (`renderAutomationRow`) or ADSR-envelope row (`renderAdsrRow`) per track when its panel is toggled open — both need the wide timeline-column width (a curve to draw, or the same row/gutter/lane sizing for visual consistency), so both render as a full extra `.track` row. The ✨ FX panel (`buildFxPanel()`) doesn't need that width — every field in it is a static per-track knob, nothing tied to a timeline column — so it renders as a compact 2-column grid appended straight into `buildHeader()`'s own left-column header instead, expanding that header's height in place rather than adding a row. There is no virtual DOM or diffing anywhere in this. **Every icon in the app** comes from one table, `GLYPHS`, via `glyph(name)` — the waveform buttons, the per-note effect toggles, the FX panel's group headings, and the whole toolbar/menu/dialog set. An entry is either a bare list of paths (the wide 24x12 waveform box) or `{ box, paths }` for the square 24x24 interface icons, so which box a glyph uses is a property of the glyph rather than something callers pass. Static markup carries `data-glyph="name"` and one boot pass fills them in; JS-built buttons use `setGlyphLabel(btn, name, label)`. The same concept is drawn the same way wherever it appears (and a per-note flag shares its glyph with the per-track control of the same name). **Emoji were removed from controls deliberately** — they rendered in the system's own colour and style; plain geometric characters that already match (the transport, undo/redo, `▾`/`▸`, `✕`, `+`/`−`) were kept on purpose, and `verify.js` pins that split with an explicit keep-list. They're stroked with `currentColor` so one copy serves every colour state, and they're `aria-hidden`: every control keeps its own text label or `aria-label`, and the waveform picker additionally spells out the selected shape's name below the row — **a new glyph is decoration, never the only name a control has**.
  - **Interaction** — mouse-driven note/hit placement, drag-move, resize, marquee-select, and multi-select are implemented as manual `mousedown`/`mousemove`/`mouseup` state machines (e.g. `startMoveNote`, `startResize`, `startMarquee`, `startScrub`, `startLoopDrag`, `startAutomationDrag`). Whether two items in a track can coexist is decided in exactly one place: `notesConflict(a, b)` (same pitch, overlapping in time) and `hitsConflict(a, b)` (same drum, same column), with `clearOverlaps(notes, probe, keep)` wrapping the former. Every path that places, drags, nudges, pastes or drops something goes through them — **use them rather than writing the comparison inline**, which is how five separate bugs got in (each hand-written variant drifted, and each drift silently deleted the user's notes or hits). Selection state follows the same rule: `state.selected` is `{ track, item }` holding the *object* — a note **or a rhythm hit**, since hits are selectable too — never an index, and `state.multiSelected` is a Set of objects scoped to `state.activeTrack` — switch tracks through `activateTrack()`/`setActive()` so it gets cleared, or a later nudge will move the old track's items into the new one. The note inspector's Chord panel builds on that by adding real notes above the selected root — distinct from the Arpeggio presets, which only set a flag on the one note — skipping any interval that clamps at the pitch ceiling onto a pitch already sounding. The voicings live in `CHORD_PRESETS` (`{label, name, intervals}`) and `addChordAbove()` is generic over the interval list, so a new chord is one table row, not another button. Both grids sit behind a `▸ presets` disclosure (`appendPalette()`/`openPalettes`, collapsed by default, remembered in `localStorage`) — they render no buttons at all while collapsed, so anything driving them has to open them first. The Arpeggio quick-fill buttons render from that same table — `note.arp` and `CHORD_PRESETS.intervals` both hold offsets *above* the root (`scheduleTone` prepends `note.freq` itself), so one palette serves both rows; they differ only in one note sweeping the voicing vs. real notes being added.
  - **Audio synthesis** — a Web Audio graph is built per note (`OscillatorNode`/`GainNode`, plus a `WaveShaperNode` for bitcrush via `bitcrushCurve()`, and a duplicate detuned oscillator for chorus). A note's sound source comes from one place, `createVoiceSource(oscType, duty, freq, fm)`: most waveforms are an oscillator, `noise` is a looping 93-sample buffer (the NES's short-mode LFSR period, so it buzzes at a pitch), `ringmod` is a carrier multiplied by a second oscillator through a `GainNode` sitting at 0, and `pwm` is a sawtooth minus a *delayed copy of itself* — a pulse train whose width is that delay, swept by an LFO on `delayTime`. **The delayed path is fed from the same oscillator, not a second one**: two would have to stay in phase for the width to hold, which Web Audio doesn't promise, and splitting one makes it exact by construction. **The sweep LFO belongs to the channel, not the note** (`chanPwmLfo`, `createChanPwmLfo()`, reached via `getTrackVoice().pwmLfo`): one free-running oscillator per track, started with the channel and never restarted, that each `pwm` note scales into its own period through a per-note `GainNode`. A per-note LFO starts at phase 0 every time, so every note began at the same 50% duty and a run of eighth notes came out as a plain square wave; sharing one makes the sweep continuous across the part. Because that oscillator outlives every note, each note's tap on it is disconnected from the oscillator's own `ended` event — **not from the returned `stop(t)`**, which runs at *schedule* time with a future `t` and would cut the sweep off before the note is even heard. A track with no channel yet (the inspector's preview) falls back to a note-local LFO. It returns `{ out, pitch, toPitch, detune, start, stop }` — `out` is what connects onward (not always the pitched node, since ring mod's output is the multiplying gain), and **`toPitch` converts Hz into whatever unit that source's pitch param uses**. Both mappings are *linear* in frequency, which is the only reason bend/vibrato/arpeggio/FM work on noise unchanged: a depth expressed as a fraction of the note's own frequency converts by the same factor as the frequency. **Add a new waveform there, not with a branch at each scheduling site** — the wave selection was hand-written four times and one copy was still reading `note.duty` instead of `effectiveDuty()` long after the others were unified, so the per-track Duty default silently never reached a portamento note. The per-track chain and the song-global master bus described below are each built by one shared function — `buildChannelChain()` and `buildMasterBus()` respectively — called from all three places a context gets (re)built: `ensureCtx()` (live playback), `ensureChannelNodes()` (adding a track mid-session) and `renderSongToWav()` (offline export); these three used to duplicate that construction code line-for-line. The one real difference offline: `buildMasterBus()`/`buildChannelChain()` return each bitcrush insert's worklet-upgrade promise (see `ensureCrusher()`/`ensureTrackCrusher()`), which `renderSongToWav()` awaits before calling `startRendering()` since an offline render happens once, deterministically (unlike live playback, which can let the bypass-then-upgrade swap happen in place over an inaudible handful of milliseconds). Per-note effects (bend, vibrato, tremolo, duty/pulse-width, arpeggio, portamento, bitcrush, echo, chorus) are applied at playback time from properties on the note object itself, not from separate effect tracks. The five things a *track* contributes to a note's sound — ADSR, filter, FM, vibrato and the `square` pulse-width default — travel together as one `voice` object (`getTrackVoice()`/`DEFAULT_VOICE`) rather than a tail of positional parameters on `scheduleTone()`/`schedulePortamentoTone()`; add a new per-track synth setting as a field there. Duty resolves in exactly one place, `effectiveDuty(note, voice)` (**the note's own value overrides the track's, `null` inherits**), and the oscillator's shape is picked in exactly one place, `setOscWave()` — that branch used to be hand-written three times (main osc, chorus osc, portamento osc). Drum hits have no such flags, but they do have a velocity: all ten kit sounds are played through one dispatch point, `scheduleDrum()`, which applies `hitVel()` as a plain `GainNode` in front of the destination — **don't add a `vel` argument to the individual schedulers**, each of which hand-writes its own multi-stage envelope (the snare has two, the clap three) and would be ten chances for the same scaling to drift. At full velocity `scheduleDrum` inserts no node at all, so an untouched song builds the identical graph it did before. Each track's ADSR envelope (`applyAdsrEnvelope()`) shapes the note's gain; each track's volume/pan/Delay-send/Chorus-send/Reverb-send automation curve (`state.automation`, `AUTOMATION_PARAMS`) is scheduled as native `AudioParam` ramps once per playback chunk (`scheduleAutomationForChunk()`), independent of note-level effects. Separately, every track (tonal or rhythm) also has a continuous Delay-, Chorus- and Reverb-send knob (`state.fxSend`, `getFxSend()`/`setFxSend()`, the ✨ FX panel) that taps `chanGain[id]` into three shared global effect buses (`createGlobalFxBuses()`/`createTrackFxSends()`, the reverb bus reusing `ensureReverbImpulse()`'s impulse response — which, like the two drum noise buffers (`ensureNoiseBuffer()`/`ensureCrashNoiseBuffer()`), is filled from a **seeded** `mulberry32()` stream rather than `Math.random()`, so the same song renders to the same bytes every time; each buffer gets its own generator, since one shared stream would make each buffer's contents depend on which others happened to be built first) — unlike the per-note echo/chorus/reverb above this needs no per-note flag and works on rhythm tracks too, since it taps the one node every sound on a track already passes through rather than any synthesis-time plumbing. The same panel also has a per-track 3-band EQ and Compressor — unlike the sends these are inserts (`chanGain[id]` → `chanEq[id]`'s three biquads → `chanComp[id]` → …). The EQ (`state.eq`, `getTrackEq()`/`setTrackEq()`, `createChanEq()`) reuses the master EQ's band layout (200Hz shelf / 1kHz peak / 4kHz shelf, ±12dB) and sits *first* so the compressor reacts to the shaped signal; the Compressor (`state.comp`, `getTrackComp()`/`setTrackComp()`) has the same parameters/"neutral by default" contract (`ratio: 1`) as the master compressor below. Note `chanEq[id]` is a `{low, mid, high}` object rather than a single node, so `removeTrack()` disconnects its bands explicitly instead of via the generic node loop. Two more inserts follow the compressor in that same chain: a per-track Bitcrush downsampler (`state.crush`, `getTrackCrush()`/`setTrackCrush()`, `chanComp[id]` → `chanCrush[id]` once its `AudioWorkletNode` has loaded → …) reusing the master bus's own `crushAmountToHold()`/`js/downsample-processor.js` — independent of the per-note Crush flag, which is a fixed always-on effect rather than a dial-able amount — and a per-track Tremolo (`state.tremolo`, `getTrackTremolo()`/`setTrackTremolo()`, an LFO added onto a plain `GainNode`'s own `.gain` `AudioParam`, the same trick the chorus bus below uses on `delayTime`). A per-track **Vibrato** (`state.vibrato`, `getTrackVibrato()`/`setTrackVibrato()`) is the pitch counterpart of that tremolo and the one entry in `TRACK_FX_REGISTRY` that is **not** an insert: an LFO on the channel gain can shape an already-summed signal, but bending its pitch cannot happen downstream — it has to reach each note's own oscillator. So it is threaded into `scheduleTone()`/`schedulePortamentoTone()` beside the ADSR/filter/FM settings (`addTrackVibrato()`, depth in cents via `centsToRatio()`), which also makes it the registry's only `tonalOnly: true` entry — a drum hit has no oscillator to bend, so `trackFxFor(track)` filters it out of a rhythm track's panel and `applySavedMix()` skips it there. Its `apply` is a deliberate no-op: a note's LFO is created with the note, so a change lands on the next scheduled chunk, exactly as a waveform/ADSR/filter change does. It **adds to** the per-note `vib` flag rather than replacing it — both connect an LFO into the same `osc.frequency`, and `AudioParam` inputs sum. `chanTremolo[id]` is the fixed end of that insert chain that `chanPan[id]`/the VU meter/the three FX sends all connect from, so a bitcrushed/tremolo'd track's pan, meter and sends all reflect the final processed signal. These five effects' state shape/UI (not their audio-graph wiring, which stays as the separate functions above — too heterogeneous to be worth unifying) are driven by one table, `TRACK_FX_REGISTRY` (get/set/apply functions plus each field's range/format/clamp-on-load rules), so both `applySavedMix()`'s load/validate logic and `buildFxPanel()`'s rendering iterate the same data instead of one hand-written block per effect. All channels sum into `masterGain`, which then runs through a song-global 3-band EQ + `DynamicsCompressorNode` (`buildMasterFXChain()`/`applyMasterFX()`, `state.masterEQ`/`state.masterComp`, editable via the 🎛️ panel in the master strip) before `ctx.destination`; defaults are fully neutral (0dB, ratio 1:1) so this is a no-op unless a song explicitly sets it.
  - **Accessibility** — the grid is positioned `<div>`s, so none of it is accessible for free. Landmarks (`<main>`/`<aside>`/`role="toolbar"`), a hidden `<h1>` and a skip link give the page structure; a high-contrast `:focus-visible` ring makes keyboard focus visible (the browser default disappears on this palette). `noteAriaLabel()`/`hitAriaLabel()` name every grid item as pitch/drum + bar and beat, and lanes name themselves — **if you add a new kind of grid item, it needs a label too or it is invisible to assistive tech**. Stateful controls carry `aria-pressed` (Mute/Solo, per-note effect toggles) or `aria-checked` (the Pen/Eraser/Grab `role="radiogroup"`) rather than only a CSS class. Keyboard grid access is Shift+←/→ to step the selection and Home/End to jump, announced via `announce()` into `#a11y-status`; plain arrows still nudge, and notes use a roving tabindex so Tab doesn't walk through hundreds of blocks.
  - **`verify.js` steps** — when a change adds or reshapes UI, extend `verify.js` rather than writing a throwaway script (see its own section below). Two traps that have bitten repeatedly: `Array.prototype.every` returns true for an empty list, so assert the expected *count* or the expected *values* before asserting a property over them; and most selectors need scoping to one track (`.closest('.th-wave-row')`, one `.th-fx-panel`) because a loaded song has several tracks whose controls would otherwise be read as one list. Confirm a new assertion actually fails against the unfixed code before trusting it.
- **Song I/O** — the 🎵 Songs menu loads examples from `songs/` (network fetch) or user songs from `localStorage`; 💾/📂 in the toolbar export/import a song as a `.json` file. A separate "export as code" path serializes the current song into `TRACKS`/`RHYTHM_TRACKS` JS literals (matching `js/song-data.js`'s shape) for embedding back into a game — automation/ADSR/markers/song name aren't representable in that format and are intentionally left out of it. 🎹/🎼 export/import a Standard MIDI File (format 1, own SMF writer/parser, no library — `exportMidiBytes()`/`parseMidiFile()`); per-note effects have no MIDI equivalent and aren't round-tripped, and MIDI import merges all channel-9 (drum) events in a file into the song's first rhythm track. 🔊 renders the whole song offline (`OfflineAudioContext`, same synthesis path as playback — `renderSongToWav()`) and downloads a `.wav`; MP3 was deliberately left out to keep the app dependency-free.
- **`js/song-data.js`** — exports `TRACKS`, `RHYTHM_TRACKS`, `TEMPO_BPM`: the demo song's note data, in the same shape "export as code" (see above) produces. `index.html` only imports `TEMPO_BPM` from it (a fallback used in a couple of places) — the page no longer loads `TRACKS`/`RHYTHM_TRACKS` as a startup default; the full demo song is still available, but only via the 🎵 Songs menu's "Froggy Hop" example (`songs/froggy-hop.json`, a separate, more fully-featured file — see below).
- **`songs/`** — example songs as JSON (`froggy-hop.json`, `cinematic.json`, `techno.json`, `neon-drive.json`) plus `index.json`, which lists `{file, name, desc}` entries consumed by the in-app Songs menu. Adding an example song means dropping a `.json` file here and adding an entry to `index.json`.
- **`dev-server.js`** — a dependency-free static file server (Node `http`/`fs`) used only for local development. **`dev.js`** wraps it for interactive use — spawns it, polls until it's actually responding, then shells out to the platform's "open a URL" command (`open`/`xdg-open`/`start`) to launch the default browser; `dev-server.js` itself stays plain since it's also run headlessly (e.g. browser-driven verification), where auto-opening a browser would be unwanted or fail outright. **`start.cmd`** is a Windows double-click entry point (`cd` to its own folder, check `node` is on `PATH`, then run `node dev.js`) for people who'd rather not open a terminal.
- **`verify.js`** — a permanent headless-browser smoke test: starts its own `dev-server.js` on a throwaway port, drives the app through a handful of core interactions (loads blank, loads an example song, Automation/FX panels, playback, add/undo a track), and fails if any expectation is wrong *or* if the page logs a console error/uncaught exception at any point during the run. Talks to the browser directly over the Chrome DevTools Protocol (`WebSocket` + JSON-RPC, using only Node's own built-ins) instead of a browser-automation library, matching the project's no-dependencies rule rather than introducing this repo's first npm dependency; `element.click()`/`dispatchEvent()` via `Runtime.evaluate()` stands in for what a library like Playwright would otherwise provide. Auto-discovers a local Chromium-family browser (`CHROME_PATH` env var to override). Not a real test suite — one reusable script covering the kind of regression check that used to mean writing a one-off Playwright script by hand for every feature.
- **`manifest.webmanifest` / `sw.js` / `icons/`** — PWA support: the manifest (linked from `index.html`'s `<head>`) makes the site installable (Android "Add to Home screen", `display_override: ["fullscreen", "standalone"]`); `sw.js` precaches the app shell (index.html, song-data.js, bundled songs, icons) for offline use and is registered from the bottom of `index.html`'s script. Bump `CACHE_NAME` in `sw.js` when precached files change so installed clients pick up the update. Icons were generated with a one-off Node script (not checked in) using a plain PNG encoder — regenerate similarly if they ever need to change.
- **`.github/workflows/pages.yml`** — deploys the whole repo root to GitHub Pages via GitHub Actions on push to `main` (`.nojekyll` ensures files are served as-is).

## Working in `index.html`

Since the whole app lives in one file with no module boundaries beyond `song-data.js`, most changes require understanding how `state` flows into `render()` — mutate `state`, then call `render()` (and usually `autosave()`) rather than patching the DOM directly. Grid/timing math (`snapToGrid`, `quant`, `eighthsPerBar`/`eighthsPerBeat`, `clampCols`) is centralized near the top of the script and used throughout rendering and interaction code — reuse it instead of re-deriving column/pixel conversions locally.
