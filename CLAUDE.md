# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Web Audio Studio — a browser-based 8-bit chiptune editor. Everything is synthesised live with the Web Audio API: no audio files, no dependencies, no build step. The entire app is a single self-contained `index.html` (HTML + CSS + JS in one file) plus a small song-data module.

It was extracted from the [Frog vs Toad](https://github.com/Ruperto72/frogger-multiplayer) game; that game's soundtrack ships here as the demo song.

## Commands

```bash
node dev-server.js        # serve the repo root at http://localhost:8080
node dev.js                # same, but also opens it in your default browser once it's up
start.cmd                  # Windows: double-click to do the same (just runs `node dev.js`)
node verify.js              # headless smoke test — see below
```

Any static file server works (e.g. `python3 -m http.server 8080`) — a server is required because ES modules don't load from `file://`. There is no build or lint command, and no test framework; there are no dependencies to install. `verify.js` is the closest thing to a test command: a single, permanent, dependency-free regression check (see its own section below) — not a substitute for actually exercising a change in a real browser, but a reusable net for the kind of "did I break something" question that used to mean writing a one-off Playwright script by hand every time.

## Architecture

- **`index.html`** — the entire application (~3800 lines) inside a single `<script type="module">`. There is no component framework and no bundler; everything is plain DOM manipulation (`createElement`, `addEventListener`) driven by a central `state` object and a `render()` function that rebuilds the DOM from state. Treat this file as several logical sections rather than a list of functions:
  - **State & song model** — `state` holds tracks, notes/hits, selection, playhead, loop range, grid, tempo, mix (gain/pan/mute/solo), per-track automation curves, per-track ADSR envelopes, history stack, etc. Tonal tracks store notes as `{start, dur, ...}`-style objects; rhythm tracks store hits (10 types: kick/snare/rim/hihat/openhat/shaker/tom/clap/crash/ride, `RHYTHM_ROWS`), each with an optional `vel` (0.1–1, **absent means full** — see `hitVel()`, and note that the inspector deletes the property rather than storing `vel: 1`, so a song that never touched velocity serialises exactly as before). There can be more than one rhythm track — all share the same fixed 10-piece palette (which *kit* those pieces are synthesised as is per track, see `DRUM_KITS` below), always stay grouped after every tonal track (`RHYTHM_TRACK_IDS`, mirroring `PITCH_TRACKS`), and at least one always exists. Helper functions like `toColumnNotes`/`fromColumnNotes` and `toColumnHits`/`fromColumnHits` convert between the internal sequence format and the grid-column representation used for editing. The built-in instrument presets live in one table too, `BUILTIN_PRESETS` — each row is a `{waveform, adsr, filter, fm, duty}` in exactly the shape a *saved* preset has, so loading one is the same code path (`applyPresetToTrack()`) and saving over it afterwards is an ordinary user preset. **They are settings, not code**: the engine already had FM, a filter with its own envelope and a per-note ADSR — an electric piano is a high FM ratio at low depth, so it is a table row rather than a feature. An acoustic grand is deliberately absent: that needs samples, and the cost is that a song's `.json` stops being self-contained (see `TODO.md`'s sampling entry). A new instrument is one row, inside the ranges the Env panel can show. The built-in grooves the Patterns dialog stamps in live in one table, `RHYTHM_PATTERNS` — each entry is a one-bar `hits` list authored at 8 eighths/bar (`insertPatternIntoRhythm()` scales to the song's real `eighthsPerBar()`), plus a one-bar `fill` in the same shape. A `start` may be fractional — the column unit is an eighth but positions re-lattice to `MICRO` (1/6 of one), so `0.5` is a 16th and `1/3` a triplet, the same lattice the grid dropdown offers. Three optional fields let a pattern bring editor state or a behaviour change with it: `swing` → `state.swing` (shuffle isn't shuffle without it), `grid` → `state.grid` (**a 16th-note groove must set this**, since a hit's block is drawn one *grid step* wide, so two 16ths on the default 1/8 grid render one on top of the other), and `crashAfterFill: false` to decline the crash the bar after a fill (bossa nova's fill flips the clave rather than building). Hits carry `vel` under the same **absent means full** rule as everywhere else, so `patternHitAt()` only copies the property across when it is actually below 1. Stereo position is *not* per hit: `KIT_PAN` gives each of the ten pieces one place in the field (kick/snare centred, hi-hat and ride right, shaker/toms/crash left), applied on insert and switchable off with the dialog's "Spread the kit in stereo" checkbox — a hi-hat sits where a hi-hat sits in every groove that has one, so a per-hit `pan` would be twelve patterns' worth of the same numbers to keep in step. A pattern's own hit may still override it, and `patternPan()` is the one resolver so the dialog's ▶ preview and Insert cannot disagree. Fills land on the last bar of each `patternFillEvery`-bar phrase (`FILL_EVERY_CHOICES`, counted from the *insert* bar rather than bar 1 of the song) and the bar after a fill opens with a crash — added through `hitsConflict()` rather than blindly, since Breakbeat already crashes on its own downbeat. **A new groove is one table row**, `fill` included; nothing about phrasing or velocity is per-pattern code.
  - **Autosave / undo / history** — `autosave()` persists the current song to `localStorage` in the background as a crash-recovery safety net; it's write-only, never read back automatically — the page always boots into the starter layout (`STARTER_TRACKS` — Lead/Harmony/Bass/Pad plus the kit — built by `starterProject()`, which the Songs dialog's "Starter tracks" button also calls, so there is no second copy of the layout) rather than restoring that draft or loading the demo song, so song selection always goes through the explicit Songs menu instead. `commitHistory()`/`undo()`/`redo()` maintain a separate in-memory snapshot stack (`snapshotSong()`/`restoreSnapshot()`) for the current session's own undo history. **The sparse per-track settings (`automation`, `adsr`, `filter`, `fm`, `fxSend`, `comp`, `crush`, `tremolo`, `vibrato`, `duty`, `eq`, `activeFx`, `kit` — every map where `state[key][trackId]` absent means "the default") are named once, in `SPARSE_TRACK_MAPS`, and every place that saves, restores, clears or removes them walks that list — add a new per-track map there, not at the call sites.** Six places used to hand-write their own copy of it and four had drifted apart: `restoreTrackList()` cleared two of eleven, so loading song B kept song A's filter/FM/sends/EQ/comp/crush/tremolo on every track id the two shared (and every song has a `rhythm`); `createNewSong()` forgot `filter`/`fm`; `removeTrack()` forgot `filter`; and `applySavedMix()` never read `duty` back, so a saved pulse width was written to every file and silently dropped on load. The seeded maps (`tracks`/`gains`/`waveform`/`pan`/`mute`/`solo`) stay out of the list on purpose — those get one entry per track with a real default, so they're rebuilt from the track list rather than cleared. `autosave()` writes `currentSongData()` itself rather than a second copy of its field list.
  - **Rendering** — `render()` is the single entry point that redraws tracks, timeline, markers, playhead, loop handles, and scrollbar. Track lanes are rebuilt per-render (`renderTracks`, `renderPitchTrack`, `renderRhythmTrack`), with an optional extra automation-curve row (`renderAutomationRow`) or ADSR-envelope row (`renderAdsrRow`) per track when its panel is toggled open — both need the wide timeline-column width (a curve to draw, or the same row/gutter/lane sizing for visual consistency), so both render as a full extra `.track` row. Per-track FX are split across two places on purpose: the header carries a wrapping row of **chips** (`buildFxPanel()`/`buildFxChip()`) that are a letter and an icon — status and navigation, no knobs — and the **inspector column** carries the actual controls (`renderTrackStrip()`/`buildStripSection()`), showing the active track's whole insert chain whenever no note is selected. The chips used to carry the knobs too, via a popover per effect; measured, that made a seven-effect chip row 152px over six lines and the header 260x371, so two tracks filled the whole DAW viewport. Letter+icon chips are 44px, the row is 46px and the header 265px. **There is one editing surface per value** — the per-insert popover was retired rather than kept alongside the strip, and bypass/remove live in the strip section head only. **The master bus takes the same strip**: its chips (`MASTER_FX_REGISTRY`/`renderMasterFxChips()` — a table parallel to `TRACK_FX_REGISTRY`, deliberately separate since master's five groups are fixed and order-bound and have no bypass/remove machinery; `buildKnob()` *is* shared, taking a label and default rather than a track/effect pair) are status and navigation too, and `renderMasterStrip()`/`buildMasterStripSection()` put all five groups in the inspector column. **Who owns the inspector column is one value**, `inspectorOwner` (a track id or `'master'`), with `stripFocusKey` a bare effect key belonging to it; `setInspectorOwner()` clears the focus on any owner change, so the two cannot disagree. It is **not** `state.activeTrack = 'master'` — every nudge/paste/step-entry/pattern path reads `activeTrack` as a real track id — so the two travel together for tracks (every path that moves `activeTrack` calls `setInspectorOwner()`) and diverge only for the bus. Master's dim-when-neutral state is recomputed from the live value rather than stored, so a knob commit refreshes the chip row and the section's own class **in place**; going through `render()` there would rebuild the element the pointer is still dragging and drop focus off the dial. With master's popovers gone the floating FX popover is gone from the app entirely, `.th-fx-popover*` CSS included — `#floating-layer` now carries only menus. The header activates its track from **one guard on the container** (`e.target.closest('input, button, select, .th-name')` → ignore), not a `stopPropagation` line per control: that was sixteen lines nothing could remind you to add, and forgetting one let the header re-render under a half-finished click and swallow it. `.th-name` is in the list because it renames on double-click without being a form element. The track header itself (`buildHeader()`, 260px) is an identity row plus three captioned sections — **Osc** (the waveform picker + Auto/Env/Preset), **Inserts** (`buildFxPanel()`'s chips) and **Output** (volume/pan/VU). **Anything that floats — the waveform listbox and the Inserts `+` menu — is portal-rendered into `#floating-layer` by `renderFloatingLayer()`, never nested in `.daw`**: `.daw`'s `overflow-x: auto` computes `overflow-y: auto` too, so a descendant that extends past its box is clipped and no z-index can undo an ancestor's overflow clip (this is why the `+` menu once rendered invisibly). That pass runs *after* `renderTracks()`, since it finds each trigger by `data-track`/`data-key` in the DOM that pass just rebuilt, and anchors the popup to its rect. Light dismiss is by hand (`anyFloatingMenuOpen()`/`closeAllFloatingMenus()`): outside click, Escape, or a **vertical** `.daw` scroll only — closing on horizontal scroll too fired on `followPlayhead()`'s auto-scroll and killed knob drags mid-playback, and `.track-header` is `position: sticky; left: 0` so it never moves sideways anyway. There is no virtual DOM or diffing anywhere in this — **and that is where the render cost sits**: measured, an expanded track header is ~9.5ms per render (headless, no GPU) while the same track collapsed is 1/38 of that, and switching on every effect on every track doesn't show up in the measurement at all. The grid blocks are not the problem; laying the headers out is — **not** building them, which a cache with a 100% hit rate and no speed-up settled, and not something `content-visibility: auto` can skip either (3-4x faster, but a skipped row reports its placeholder height and the playhead stops short of the last track). Both dead ends are written up rather than left to be rediscovered. See DESIGN.md B.4 for the table and a one-liner that re-measures it. **Every icon in the app** comes from one table, `GLYPHS`, via `glyph(name)` — the waveform picker, the per-note effect toggles, the FX chips and strip sections, the master chips, each individual envelope/filter control, and the whole toolbar/menu/dialog set. An entry is either a bare list of paths (the wide 24x12 waveform box) or `{ box, paths }` for the square 24x24 interface icons, so which box a glyph uses is a property of the glyph rather than something callers pass. Static markup carries `data-glyph="name"` and one boot pass fills them in; JS-built buttons use `setGlyphLabel(btn, name, label)`. The same concept is drawn the same way wherever it appears (and a per-note flag shares its glyph with the per-track control of the same name) — but **no two *different* effects share one**, which is why the three sends stopped drawing a generic `send` arrow that left Delay/Chorus/Reverb distinguishable only by their chip letter, i.e. by position rather than identity. **Emoji were removed from controls deliberately** — they rendered in the system's own colour and style; plain geometric characters that already match (the transport, undo/redo, `▾`/`▸`, `✕`, `+`/`−`) were kept on purpose, and `verify.js` pins that split with an explicit keep-list. They're stroked with `currentColor` so one copy serves every colour state, and they're `aria-hidden`: every control keeps its own text label or `aria-label`, and the waveform picker spells its shape's name out beside the glyph on both the trigger and every option — **a new glyph is decoration, never the only name a control has**.
  - **Interaction** — mouse-driven note/hit placement, drag-move, resize, marquee-select, and multi-select are implemented as manual `pointerdown`/`pointermove`/`pointerup` state machines (**pointer events, not mouse** — one path covers mouse, touch and pen; the `mousedown` listeners left in the file are only `stopPropagation()` guards) (e.g. `startMoveNote`, `startResize`, `startMarquee`, `startScrub`, `startLoopDrag`, `startAutomationDrag`). Whether two items in a track can coexist is decided in exactly one place: `notesConflict(a, b)` (same pitch, overlapping in time) and `hitsConflict(a, b)` (same drum, same column), with `clearOverlaps(notes, probe, keep)` wrapping the former. Every path that places, drags, nudges, pastes or drops something goes through them — **use them rather than writing the comparison inline**, which is how five separate bugs got in (each hand-written variant drifted, and each drift silently deleted the user's notes or hits). `state.activeFx` is **not** an on/off switch for an effect: every effect already exists in the audio graph for every track (`createTrackFxSends()` builds all three sends unconditionally, the inserts are neutral by default), so it only records which effects the panel *shows* plus each one's bypass flag — and only `isFxBypassed()` ever reaches the audio. `visibleFxFor()` therefore shows a chip when the effect is non-default **or** when a send carries an automation curve (`fxHasAutomation()`), and `removeFxChip()` clears that curve (`clearFxAutomation()`) — removal is not bypass, so a curve left behind would keep playing with nothing on screen to explain it. `FX_AUTOMATION_PARAM` names the three sends as the only automatable inserts, once, beside `AUTOMATION_PARAMS`. Selection state follows the same rule: `state.selected` is `{ track, item }` holding the *object* — a note **or a rhythm hit**, since hits are selectable too — never an index, and `state.multiSelected` is a Set of objects scoped to `state.activeTrack` — switch tracks through `activateTrack()`/`setActive()` so it gets cleared, or a later nudge will move the old track's items into the new one. The note inspector's Chord panel builds on that by adding real notes above the selected root — distinct from the Arpeggio presets, which only set a flag on the one note — skipping any interval that clamps at the pitch ceiling onto a pitch already sounding. The voicings live in `CHORD_PRESETS` (`{label, name, intervals}`) and `addChordAbove()` is generic over the interval list, so a new chord is one table row, not another button. Both grids sit behind a `▸ presets` disclosure (`appendPalette()`/`openPalettes`, collapsed by default, remembered in `localStorage`) — they render no buttons at all while collapsed, so anything driving them has to open them first. The Arpeggio quick-fill buttons render from that same table — `note.arp` and `CHORD_PRESETS.intervals` both hold offsets *above* the root (`scheduleTone` prepends `note.freq` itself), so one palette serves both rows; they differ only in one note sweeping the voicing vs. real notes being added.
  - **Audio synthesis** — a Web Audio graph is built per note (`OscillatorNode`/`GainNode`, plus a `WaveShaperNode` for bitcrush via `bitcrushCurve()`, and a duplicate detuned oscillator for chorus). A note's sound source comes from one place, `createVoiceSource(oscType, duty, freq, fm)`: most waveforms are an oscillator, `noise` is a looping 93-sample buffer (the NES's short-mode LFSR period, so it buzzes at a pitch), `ringmod` is a carrier multiplied by a second oscillator through a `GainNode` sitting at 0, and `pwm` is a sawtooth minus a *delayed copy of itself* — a pulse train whose width is that delay, swept by an LFO on `delayTime`. **The delayed path is fed from the same oscillator, not a second one**: two would have to stay in phase for the width to hold, which Web Audio doesn't promise, and splitting one makes it exact by construction. **The sweep LFO belongs to the channel, not the note** (`chanPwmLfo`, `createChanPwmLfo()`, reached via `getTrackVoice().pwmLfo`): one free-running oscillator per track, started with the channel and never restarted, that each `pwm` note scales into its own period through a per-note `GainNode`. A per-note LFO starts at phase 0 every time, so every note began at the same 50% duty and a run of eighth notes came out as a plain square wave; sharing one makes the sweep continuous across the part. Because that oscillator outlives every note, each note's tap on it is disconnected from the oscillator's own `ended` event — **not from the returned `stop(t)`**, which runs at *schedule* time with a future `t` and would cut the sweep off before the note is even heard. A track with no channel yet (the inspector's preview) falls back to a note-local LFO. It returns `{ out, pitch, toPitch, detune, start, stop }` — `out` is what connects onward (not always the pitched node, since ring mod's output is the multiplying gain), and **`toPitch` converts Hz into whatever unit that source's pitch param uses**. Both mappings are *linear* in frequency, which is the only reason bend/vibrato/arpeggio/FM work on noise unchanged: a depth expressed as a fraction of the note's own frequency converts by the same factor as the frequency. **Add a new waveform there, not with a branch at each scheduling site** — the wave selection was hand-written four times and one copy was still reading `note.duty` instead of `effectiveDuty()` long after the others were unified, so the per-track Duty default silently never reached a portamento note. The per-track chain and the song-global master bus described below are each built by one shared function — `buildChannelChain()` and `buildMasterBus()` respectively — called from all three places a context gets (re)built: `ensureCtx()` (live playback), `ensureChannelNodes()` (adding a track mid-session) and `renderSongToWav()` (offline export); these three used to duplicate that construction code line-for-line. The one real difference offline: `buildMasterBus()`/`buildChannelChain()` return each bitcrush insert's worklet-upgrade promise (see `ensureCrusher()`/`ensureTrackCrusher()`), which `renderSongToWav()` awaits before calling `startRendering()` since an offline render happens once, deterministically (unlike live playback, which can let the bypass-then-upgrade swap happen in place over an inaudible handful of milliseconds). Per-note effects (bend, vibrato, tremolo, duty/pulse-width, arpeggio, portamento, bitcrush, echo, chorus, pan) are applied at playback time from properties on the note object itself, not from separate effect tracks. Per-note **pan** (`notePan()`, **absent means centred**) is a `StereoPannerNode` inserted in `connectVoiceOutput()` last before the destination, so it sits inside the track's own pan rather than fighting it; the echo/reverb taps stay on the pre-pan node so a hard-panned note doesn't drag its tail with it. At centre no node is built, and a panned note also opts out of the voice pool the way a bitcrushed one does (a pooled voice is wired to the destination once, so there is nowhere to put a panner). Pooling (`acquireVoice()`/`voiceGainFor()`, `VOICE_POOL_SIZE = 16` per channel) hands a note the gain+filter pair of a voice whose previous note has finished, rather than building a new one — measured at 24 filters for 117 notes on the demo song, against 108 unpooled. A voice frees up at `startAt + dur + VOICE_RELEASE_PAD`, **not** at `startAt + dur`: `envelopeTimes()` ends the release exactly at `startAt + dur`, so reusing at that instant makes `voiceGainFor()`'s `cancelScheduledValues(startAt)` delete the release ramp's own end event and the gain jumps to silence instead of ramping there — a click on every pair of back-to-back notes. That the end event is caught rather than spared is the spec's wording, not an inference: `cancelScheduledValues` "cancels all scheduled parameter changes with times **greater than or equal to** `cancelTime`", and cancelling an active automation "may cause discontinuities" (Web Audio 1.1, §AudioParam). Two other spec facts the code leans on: `applyAdsrEnvelope()`'s `0.0001` floors are load-bearing, since **an exponential ramp cannot reach or leave zero** ("if V0 is zero, then v(t) = V0 … an exponential ramp to 0 is not possible") — start the attack at 0 and every note is silent; and a stopped source **outputs silence rather than disappearing**, which is why a spent tremolo LFO left connected to a pooled gain contributes 0 to the next note rather than needing to be disconnected. The six things a *track* contributes to a note's sound — ADSR, filter, FM, vibrato, the `square` pulse-width default and the free-running PWM sweep LFO — travel together as one `voice` object (`getTrackVoice()`/`DEFAULT_VOICE`) rather than a tail of positional parameters on `scheduleTone()`/`schedulePortamentoTone()`; add a new per-track synth setting as a field there. Duty resolves in exactly one place, `effectiveDuty(note, voice)` (**the note's own value overrides the track's, `null` inherits**), and the oscillator's shape is picked in exactly one place, `setOscWave()` — that branch used to be hand-written three times (main osc, chorus osc, portamento osc). Drum hits have no such flags, but they do have a velocity: all ten kit sounds are played through one dispatch point, `scheduleDrum()`, where **velocity is tone as well as level**: below full it inserts a `GainNode` *and* a lowpass whose cutoff rises with velocity (`velocityCutoff()`, interpolated in log space because brightness is perceived that way — a linear sweep would spend most of its travel where the ear cannot separate it). Hitting a drum harder excites its high modes, so velocity that only scaled gain sounded like one sample turned down, which is what a machine sounds like and a player does not. One filter at the dispatch point does this for all ten pieces; the alternative was editing ten hand-written envelopes. No scheduler builds a lowpass of its own (they use bandpass and highpass only), which is what lets `verify.js` identify this one unambiguously. It applies `hitVel()` as a plain `GainNode` and `hitPan()` as a `StereoPannerNode` in front of the destination — **don't add `vel`/`pan` arguments to the individual schedulers**, each of which hand-writes its own multi-stage envelope (the snare has two, the clap three) and would be ten chances for the same value to drift. Both are absent-means-neutral: at full velocity and centre `scheduleDrum` inserts no node at all, so an untouched song builds the identical graph it did before. The chain is built backwards from the destination so pan ends up *last*, matching where a note's own panner sits. **Which kit those ten pieces are synthesised as is one table**, `DRUM_KITS` (`retro`/`eighties`/`acoustic`): each entry is a plain object of the frequencies, decays and levels the ten schedulers read, and every scheduler takes `(startAt, destGain, kit)` and reads `kit.snare.noiseDecay` where it used to carry the number inline. `retro` holds *exactly* the numbers that were inline before, so the default sound is unchanged by construction rather than by ear — **a new kit is one table row, not an eleventh scheduler**. The choice is per rhythm track (`state.kit`, `getTrackKit()`/`getTrackKitId()`/`setTrackKit()`, `DEFAULT_KIT`), lives in `SPARSE_TRACK_MAPS` so save/load/undo/track-removal came free, and follows the same **absent means the default** rule as everything else there — a song written before kits existed has no `kit` key and loads as retro, which is what it was written as. The kit id is threaded through `scheduleDrum(type, startAt, destGain, vel, pan, kitId)` from every calling site rather than read from `state` inside the schedulers, so an offline render and the pattern-dialog preview resolve it the same way playback does. Three schedulers (snare/crash/ride, plus the clap's spread copies) had to start setting `src.loop`: an 80s crash rings 1.6s and the shared noise buffers are 0.1s/0.9s, so a decay that outlasts its buffer would otherwise fall silent mid-tail. **The kit picker and the waveform picker are one control**: a track has a waveform or a kit and never both, so they share the trigger (`.th-osc-trigger`), the styling, `oscPickerOpen` and the light-dismiss machinery, and `renderFloatingLayer()` picks `buildFloatingKitMenu` or `buildFloatingOscMenu` from `isRhythm(oscPickerOpen)`. The section is captioned **Kit** rather than **Osc** on a rhythm track — it has no oscillator. Two earlier versions were worse and both failures are worth keeping in mind: a half-width native `<select>` under an "Osc" heading, which was reported as the feature being *missing*; and then that same `<select>` at full width, which still made the rhythm track look like it had a lesser control than every other track and left the three kits distinguishable only by reading their names. Each kit therefore names its own glyph in its `DRUM_KITS` row (`kitRetro`/`kitEighties`/`kitAcoustic`, resolved through `kitGlyphOf()`), so a new kit is still **one table row** including its picture. Those three glyphs draw the **shape of a hit's decay** — a narrow spike, a tail cut off by a vertical wall, a long smooth taper — because that is what a kit row is a table of; they share a baseline and a strike line so only the tail differs. **A `.track` row now states its own kind** (`data-kind="pitch"`/`"rhythm"`, set in `renderPitchTrack()`/`renderRhythmTrack()`). Anything that needs to tell the two apart reads that instead of inferring it from a control that happens to be on one and not the other — `verify.js` had eighteen places keyed on "has a waveform trigger", and five steps broke at once the moment the kit picker started using that same trigger. Each track's ADSR envelope (`applyAdsrEnvelope()`) shapes the note's gain; each track's volume/pan/Delay-send/Chorus-send/Reverb-send automation curve (`state.automation`, `AUTOMATION_PARAMS`) is scheduled as native `AudioParam` ramps once per playback chunk (`scheduleAutomationForChunk()`), independent of note-level effects. Separately, every track (tonal or rhythm) also has a continuous Delay-, Chorus- and Reverb-send knob (`state.fxSend`, `getFxSend()`/`setFxSend()`, the FX panel) that taps `chanGain[id]` into three shared global effect buses (`createGlobalFxBuses()`/`createTrackFxSends()`, the reverb bus reusing `ensureReverbImpulse()`'s impulse response — which, like the two drum noise buffers (`ensureNoiseBuffer()`/`ensureCrashNoiseBuffer()`), is filled from a **seeded** `mulberry32()` stream rather than `Math.random()`, so the same song renders to the same bytes every time; each buffer gets its own generator, since one shared stream would make each buffer's contents depend on which others happened to be built first) — unlike the per-note echo/chorus/reverb above this needs no per-note flag and works on rhythm tracks too, since it taps the one node every sound on a track already passes through rather than any synthesis-time plumbing. The same panel also has a per-track 3-band EQ and Compressor — unlike the sends these are inserts (`chanGain[id]` → `chanEq[id]`'s three biquads → `chanComp[id]` → …). The EQ (`state.eq`, `getTrackEq()`/`setTrackEq()`, `createChanEq()`) reuses the master EQ's band layout (200Hz shelf / 1kHz peak / 4kHz shelf, ±12dB) and sits *first* so the compressor reacts to the shaped signal; the Compressor (`state.comp`, `getTrackComp()`/`setTrackComp()`) has the same parameters/"neutral by default" contract (`ratio: 1`) as the master compressor below. Note `chanEq[id]` is a `{low, mid, high}` object rather than a single node, so `removeTrack()` disconnects its bands explicitly instead of via the generic node loop. Two more inserts follow the compressor in that same chain: a per-track Bitcrush downsampler (`state.crush`, `getTrackCrush()`/`setTrackCrush()`, `chanComp[id]` → `chanCrush[id]` once its `AudioWorkletNode` has loaded → …) reusing the master bus's own `crushAmountToHold()`/`js/downsample-processor.js` — independent of the per-note Crush flag, which is a fixed always-on effect rather than a dial-able amount — and a per-track Tremolo (`state.tremolo`, `getTrackTremolo()`/`setTrackTremolo()`, an LFO added onto a plain `GainNode`'s own `.gain` `AudioParam`, the same trick the chorus bus below uses on `delayTime`). A per-track **Vibrato** (`state.vibrato`, `getTrackVibrato()`/`setTrackVibrato()`) is the pitch counterpart of that tremolo and the one entry in `TRACK_FX_REGISTRY` that is **not** an insert: an LFO on the channel gain can shape an already-summed signal, but bending its pitch cannot happen downstream — it has to reach each note's own oscillator. So it is threaded into `scheduleTone()`/`schedulePortamentoTone()` beside the ADSR/filter/FM settings (`addTrackVibrato()`, depth in cents via `centsToRatio()`), which also makes it the registry's only `tonalOnly: true` entry — a drum hit has no oscillator to bend, so `trackFxFor(track)` filters it out of a rhythm track's panel and `applySavedMix()` skips it there. Its `apply` is a deliberate no-op: a note's LFO is created with the note, so a change lands on the next scheduled chunk, exactly as a waveform/ADSR/filter change does. It **adds to** the per-note `vib` flag rather than replacing it — both connect an LFO into the same `osc.frequency`, and `AudioParam` inputs sum (specified, not incidental: the computed value "is the sum of the `paramIntrinsicValue` value and the value of the input AudioParam buffer"). `chanTremolo[id]` is the fixed end of that insert chain that `chanPan[id]`/the VU meter/the three FX sends all connect from, so a bitcrushed/tremolo'd track's pan, meter and sends all reflect the final processed signal. These six effects' state shape/UI (not their audio-graph wiring, which stays as the separate functions above — too heterogeneous to be worth unifying) are driven by one table, `TRACK_FX_REGISTRY` (get/set/apply functions plus each field's range/format/clamp-on-load rules), so both `applySavedMix()`'s load/validate logic and `buildFxPanel()`'s rendering iterate the same data instead of one hand-written block per effect. All channels sum into `masterGain`, which then runs through a song-global 3-band EQ + `DynamicsCompressorNode` (`buildMasterFXChain()`/`applyMasterFX()`, `state.masterEQ`/`state.masterComp`, editable via the Master FX panel in the master strip) before `ctx.destination`; defaults are fully neutral (0dB, ratio 1:1) so this is a no-op unless a song explicitly sets it.
  - **Recording & metronome** — `state.recTrack` (one armed track — there is one keyboard, so arming another moves it) and `state.metronome` are **editor state, not song content**: never serialised, never in an undo snapshot, and the metronome is remembered per browser under its own `localStorage` key the way collapse state is. The metronome is a `scheduleClick()` blip on its own `metroGain` straight to `ctx.destination`, **deliberately outside the master bus** — it is a rehearsal aid, so it must not pass the master EQ/compressor and must not exist in an offline render; the guarantee is simply that `renderSongToWav()` never calls `scheduleMetronomeForChunk()`. Swing is not applied to it on purpose: it is the straight reference the swung part is played against. **A MIDI keyboard plays into the same core**: `connectMidiInput()`/`handleMidiMessage()` (Web MIDI, omni over every input and channel) resolve a message and hand it to `recNoteDown`/`recDrumDown`/`recKeyUp`, the very functions the computer keyboard uses — so monitoring, recording and step entry cannot diverge between the two. `heldKeys` is keyed by an `id` that is an `event.code` for the computer keyboard and `midi:<note>` for MIDI, which is why the prefix exists. Velocity goes through `midiVelToVel()`, **shared with MIDI file import**, and reaches the monitoring voice as well as the stored note; drums resolve through `GM_DRUM_REVERSE`, also shared with import, and an unmapped note is dropped rather than folded onto the nearest piece. A note-on with velocity 0 is a note *off* — many keyboards never send `0x80`. The key map is `REC_KEY_SEMIS`/`REC_KEY_DRUMS`, keyed on **`event.code` rather than `event.key`** so the layout is positional and survives a non-US keyboard. Note keys are live only while a track is armed, which is what leaves the letter shortcuts (M for metronome, 1/2/3 for tools) working until you deliberately arm something. `ctxTimeToCol()` converts an audio timestamp to a column using the same `playStartCol`/`playStartCtxTime` anchor the playhead animation uses, and everything commits through `clearOverlaps()`/`hitsConflict()` like every other placement path. `releaseAllKeys()` runs on blur and in `stopPlayback()` — a key held when the window loses focus never sends its keyup, and the note would otherwise be committed with an absurd length later. The same keys do a second, different job with the transport **stopped**: `stepEntryActive()` (armed, and *nothing* rolling — plain Play with a track armed means "listen", not "type") turns them into step entry, placing a note at the playhead and moving it on one grid step. A stepped note commits on key *down* with a fixed one-step length, since with no clock running how long you lean on a key can't mean anything; the cursor is a single `stepAnchor` that the **first** key of a group fixes and only advances once the last of them is up, so keys pressed together spell a chord on one column rather than an arpeggio. `setStepPlayhead()` deliberately uses `quant()` rather than `seekTo()`'s `Math.round()` — rounding the playhead to whole eighths would drop every other step back onto the previous one on a 1/16 or triplet grid. The cursor moves in both of the grid's dimensions: `←`/`→` through time (`→` leaves a rest), `↑`/`↓` between tracks (the arm moves with it — there is only one), `Home`/`End` to the song start or **one step past this track's last item** (where you'd carry on writing, not the song end), `Backspace` back one step, clearing it. All of these shadow the selection nudge/jump/delete, which is the same trade the letter keys already make. **Every move reports what it lands on, not only where it is** (`stepContentsLabel()`/`announceStep()`, chords low to high) — a cursor that only says where it is tells you how far you've walked but nothing about what you walked over. Everything announces through `announce()`, because this — not the real-time take — is the path that makes composing without a pointer possible, and it is worth nothing if you can't tell what landed.
  - **Mobile player** — below 760px `body.player-mode` hides the toolbar, `.editor-layout` and `#hscroll` **as a group** (so a new toolbar control can't leak in by being forgotten) and shows `#player`: song name, a draggable position bar, transport, level meter and a song list built from the same two sources the Songs dialog uses. It is laid out as an **app shell, not a page**: `#player` is `100dvh` with `overflow: hidden`, the card/caption/editor-link are `flex: 0 0 auto`, and `#player-list` is the one scrolling box (`flex: 1 1 auto; min-height: 0; overflow-y: auto`) — **`min-height: 0` is load-bearing**, since a flex item's default `min-height: auto` lets the list grow to fit every song and push the transport off the top instead of scrolling. The height is `100%` chained from `<html>` (a `player-shell` class set alongside `player-mode`), **not** a viewport unit: installed as a PWA the page runs in standalone/fullscreen, where `vh`/`dvh` do not mean what they mean in a tab with an address bar — that is where the list came out squeezed while the same build looked right in Chrome. The song buttons *and* their description spans are `flex: 0 0 auto`, since a flex item with `overflow: hidden` has a zero automatic minimum and can silently lose half a line. The editor is **hidden, not unbuilt** — `render()` still runs and the player reads `visualPlayhead`/`COLS`/the master meter rather than keeping a second copy of transport state; its buttons click the editor's own. **The per-frame update hangs off `onPlayheadMove`**, a hook in `updatePlayheadPositions()`, not a direct call: the player's bindings are at the end of the module and that function runs during the boot render, so a named call would hit their temporal dead zone and kill the script. "Open the editor anyway" (a `localStorage` flag) is the way back, because a phone in landscape and a small tablet land under the same breakpoint.
  - **Accessibility** — the grid is positioned `<div>`s, so none of it is accessible for free. Landmarks (`<main>`/`<aside>`/`role="toolbar"`), a hidden `<h1>` and a skip link give the page structure; a high-contrast `:focus-visible` ring makes keyboard focus visible (the browser default disappears on this palette). `noteAriaLabel()`/`hitAriaLabel()` name every grid item as pitch/drum + bar and beat, and lanes name themselves — **if you add a new kind of grid item, it needs a label too or it is invisible to assistive tech**. Stateful controls carry `aria-pressed` (Mute/Solo, per-note effect toggles) or `aria-checked` (the Pen/Eraser/Grab `role="radiogroup"`) rather than only a CSS class. Keyboard grid access is Shift+←/→ to step the selection and Home/End to jump, announced via `announce()` into `#a11y-status`; plain arrows still nudge, and notes use a roving tabindex so Tab doesn't walk through hundreds of blocks.
  - **`verify.js` steps** — when a change adds or reshapes UI, extend `verify.js` rather than writing a throwaway script (see its own section below). Two traps that have bitten repeatedly: `Array.prototype.every` returns true for an empty list, so assert the expected *count* or the expected *values* before asserting a property over them; and most selectors need scoping to one track (`.closest('.th-wave-row')`, one `.th-fx-panel`) because a loaded song has several tracks whose controls would otherwise be read as one list. Confirm a new assertion actually fails against the unfixed code before trusting it.
- **Song I/O** — the Songs menu loads examples from `songs/` (network fetch) or user songs from `localStorage`; Save file / Load file in the menu export/import a song as a `.json` file. A separate "export as code" path serializes the current song into `TRACKS`/`RHYTHM_TRACKS` JS literals (matching `js/song-data.js`'s shape) for embedding back into a game — automation/ADSR/markers/song name aren't representable in that format and are intentionally left out of it. Export/Import MIDI move a Standard MIDI File (format 1, own SMF writer/parser, no library — `exportMidiBytes()`/`parseMidiFile()`); per-note effects have no MIDI equivalent and aren't round-tripped, and MIDI import merges all channel-9 (drum) events in a file into the song's first rhythm track. Export WAV renders the whole song offline (`OfflineAudioContext`, same synthesis path as playback — `renderSongToWav()`) and downloads a `.wav`; MP3 was deliberately left out to keep the app dependency-free.
- **`js/song-data.js`** — exports `TRACKS`, `RHYTHM_TRACKS`, `TEMPO_BPM`: the demo song's note data, in the same shape "export as code" (see above) produces. `index.html` only imports `TEMPO_BPM` from it (a fallback used in a couple of places) — the page no longer loads `TRACKS`/`RHYTHM_TRACKS` as a startup default; the full demo song is still available, but only via the Songs menu's "Froggy Hop" example (`songs/froggy-hop.json`, a separate, more fully-featured file — see below).
- **`songs/`** — example songs as JSON (`froggy-hop.json`, `cinematic.json`, `techno.json`, `neon-drive.json`) plus `index.json`, which lists `{file, name, desc}` entries consumed by the in-app Songs menu. Adding an example song means dropping a `.json` file here and adding an entry to `index.json`. `verify.js`'s **first** step (`auditBundledSongs()`, one of two checks that never open a browser — the other audits the app icon) validates all of them against what `applySavedMix()` would actually accept — unknown drums or waveforms, out-of-range values, entries missing a field the loader requires (which get dropped whole), per-track settings for a track id the song doesn't have, tonal-only settings on a rhythm track, and `index.json` matching the files on disk in both directions. Every constant it checks against is **extracted from `index.html`** rather than retyped, and extraction that stops matching throws instead of returning an empty list, so the audit can't silently pass on nothing.
- **`dev-server.js`** — a dependency-free static file server (Node `http`/`fs`) used only for local development. **`dev.js`** wraps it for interactive use — spawns it, polls until it's actually responding, then shells out to the platform's "open a URL" command (`open`/`xdg-open`/`start`) to launch the default browser; `dev-server.js` itself stays plain since it's also run headlessly (e.g. browser-driven verification), where auto-opening a browser would be unwanted or fail outright. **`start.cmd`** is a Windows double-click entry point (`cd` to its own folder, check `node` is on `PATH`, then run `node dev.js`) for people who'd rather not open a terminal.
- **`shots.js`** — regenerates `docs/img/*.png`, the screenshots `README.md` links to. Same machinery as `verify.js` (own dev-server on a throwaway port, headless Chromium over CDP, Node built-ins only) and checked in for the same reason: **re-shooting has to be a command**, or the pictures rot faster than the prose. Each shot reaches its state through the app's own gestures — the Songs menu, a chip click — so an image can never show a state the app cannot reach, and `clickFirstFxChip()` throws rather than quietly shooting an empty panel. `--force-device-scale-factor=2 --font-render-hinting=none` keeps text rendering identical between runs, so a diff shows what actually moved instead of every pixel.
- **`verify.js`** — a permanent headless-browser smoke test: starts its own `dev-server.js` on a throwaway port, drives the app through a handful of core interactions (loads blank, loads an example song, Automation/FX panels, playback, add/undo a track), and fails if any expectation is wrong *or* if the page logs a console error/uncaught exception at any point during the run. Talks to the browser directly over the Chrome DevTools Protocol (`WebSocket` + JSON-RPC, using only Node's own built-ins) instead of a browser-automation library, matching the project's no-dependencies rule rather than introducing this repo's first npm dependency; `element.click()`/`dispatchEvent()` via `Runtime.evaluate()` stands in for what a library like Playwright would otherwise provide. Auto-discovers a local Chromium-family browser (`CHROME_PATH` env var to override). Not a real test suite — one reusable script covering the kind of regression check that used to mean writing a one-off Playwright script by hand for every feature.
- **`cdp.js`** — the Chrome DevTools Protocol plumbing `verify.js`, `shots.js` and `icons.js` share: browser discovery (including the hardcoded install paths, since Chrome registers an App Paths key rather than a PATH entry), headless launch on an ephemeral port with a throwaway profile, and the WebSocket/JSON-RPC client. **These three used to hand-write their own copies and two had already drifted** — `shots.js` shipped without the install-path list and so could not find a browser at all on a machine where Chrome is not on `PATH`. Tool-specific logic stays in the tool: `verify.js` keeps its console-error tracking and `step()` harness.
- **`icons.js`** — regenerates `icons/*.png` and `icons/*.svg`, the app icon. Same machinery as `shots.js`, and checked in for the same reason: the previous icons came from a one-off script nobody kept.
- **`manifest.webmanifest` / `sw.js` / `icons/`** — PWA support: the manifest (linked from `index.html`'s `<head>`) makes the site installable (Android "Add to Home screen", `display_override: ["fullscreen", "standalone"]`); `sw.js` precaches the app shell (index.html, song-data.js, bundled songs, icons) for offline use and is registered from the bottom of `index.html`'s script. Bump `CACHE_NAME` in `sw.js` when precached files change so installed clients pick up the update. Icons are generated by **`icons.js`** (`node icons.js`) — one command, checked in. The mark is defined once there: one SVG path (the `pwm` glyph restated as a filled shape), two gradient stops, and three **framings** that differ only in background shape and motif scale — `rounded` (the manifest's `any` icons, the favicon and `icon.svg`), `bleed` (`apple-touch-icon.png`, square because Safari applies its own squircle and composites transparency against an unknown backdrop) and `maskable` (motif at 0.8, which is what fits the 80%-diameter safe circle Android launchers may crop to). **A new size is one row in `OUTPUTS`**, not a new drawing. `icons.js` draws only under `require.main === module` and exports its mark, so `verify.js`'s icon audit imports `markup()`/`OUTPUTS` and diffs the committed SVGs against what the generator actually produces — the declarations, the files on disk and the drawing all have to agree, rather than the audit merely confirming that plausible-looking files exist.
- **`.github/workflows/pages.yml`** — deploys the whole repo root to GitHub Pages via GitHub Actions on push to `main` (`.nojekyll` ensures files are served as-is).

## Working in `index.html`

Since the whole app lives in one file with no module boundaries beyond `song-data.js`, most changes require understanding how `state` flows into `render()` — mutate `state`, then call `render()` (and usually `autosave()`) rather than patching the DOM directly. Grid/timing math (`snapToGrid`, `quant`, `eighthsPerBar`/`eighthsPerBeat`, `clampCols`) is centralized near the top of the script and used throughout rendering and interaction code — reuse it instead of re-deriving column/pixel conversions locally.
